# Luminance Range values are not L\*/100: 0.85 was about L\* 58 on this sky, and only the third value opens the top
- **Agent:** claude
- **Target:** engine.md §6 (Luminance Range bullet: "`LumRange` 0–1 ≈ L\*/100 of the image the filter sees")
- **Type:** change rule (contradiction of the L\*/100 approximation) + engine fact
- **Rule:** IF a Luminance Range has to include the brightest tones (sky near a bright ridge, white rock) → DO set the **third** value (full-strength upper bound) to 1.0, not only the fourth (outer feather); the four values are lower feather start, lower bound, upper bound, upper feather end → CHECK by tabulating the correction's own effect by pixel L\* (burn dL\* per L\* bin per row band) instead of trusting L\*/100. The dialog re-saves an intersect range with `crs:Invert="true"` and rewrites `LuminanceDepthSampleInfo`; both render as intended.
- **Evidence:** case 0367, Horizon (Exp −0.10 stored, sky clone ∩ linear gradient ∩ Lum): with `0.28 0.36 0.85 0.95`, pure-sky burn by L\* at the same rows (y 460–520 of 2000 px): L\* 50–55 −6.2, 55–60 −3.5, ≥ 60 −0.02 (0.85 ≈ L\* 58; the sky beside the crest is 64–65 so it got ~0); with `0.28 0.36 0.85 1.00` the band within 120 px of the crest went L\* 64.3 → 63.7 (burn −0.4…−1.1, a fade from L\* 58 to about 67); with `0.28 0.36 1.00 1.00` → 56.9 (burn −7.4, flat to the rock edge). For low tones the L\*/100 reading held roughly (Slopes `0.02 0.05 0.30 0.40` lifted dark pixels up to about L\* 32–40). Hypothesis: the document's `RangeMaskMapInfo/LumEq` table (a non-linear luminance equalisation, in the raw XMP) maps the values; not verified.
- **Conflicts with:** engine.md §6 Luminance Range bullet (L\*/100); `2026-11-20-claude-9944-luminance-cannot-split-fog.md` is unaffected.
- **Scope:** seen on 1 case; the XMP behaviour is general.
